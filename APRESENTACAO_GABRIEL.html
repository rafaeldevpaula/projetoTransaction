1. O que é o nosso projeto no fim das contas?

Imagine que um banco tem milhões de compras de cartão e precisa calcular muito rápido:

  • Quanto dinheiro foi movimentado no total;
  • Qual foi o valor médio das compras;
  • Qual foi a compra mais cara e a mais barata;
  • Quais compras parecem fraudes (compras suspeitas).

Se você colocar uma pessoa só para somar 10 milhões de compras uma por uma, ela vai demorar bastante (isso é o modo sequencial).

Mas se você pegar essa lista de 10 milhões, cortar em 4 pedaços e entregar um pedaço para 4 pessoas calcularem ao mesmo tempo, vai terminar muito mais rápido! No nosso programa, essas "pessoas" são as threads (núcleos do processador). Isso se chama Paralelismo de Dados.

Por que é fácil dividir esse trabalho em várias threads?
Porque uma compra não tem nada a ver com a outra! Para somar o valor da compra número 50, a thread não precisa saber o que aconteceu na compra número 49. Cada uma pode ser lida de forma totalmente independente.

2. A classe da compra: Transaction.java

Esse arquivo é apenas o "molde" de cada transação. Cada compra tem 10 informações (ID, cliente, data, valor, categoria, cidade, estado, tipo, estabelecimento e forma de pagamento).

O detalhe que o professor vai gostar:
Todas as variáveis são private final e a classe não tem métodos set (só tem get).
Isso significa que, depois que a compra é criada, ninguém consegue alterar o valor dela.
Em programação paralela, isso é ótimo! Como os dados nunca mudam, várias threads podem ler as compras ao mesmo tempo na memória sem perigo de uma atrapalhar a outra ou corromper dados, e sem precisar colocar travas que deixam o programa lerdo.

3. O gerador de compras de teste: TransactionGenerator.java

Como não podemos usar dados de clientes reais de um banco por questão de privacidade, criamos um gerador que inventa compras na hora. O professor pediu no enunciado para colocar 4 tipos diferentes de compras:

switch (index % 4) { case 0 -> value = 20 + random.nextDouble() * 4980; // 1. Valores variados comuns case 1 -> value = Math.max(10, 1800 + random.nextGaussian() * 1000); // 2. Compras em torno de uma média case 2 -> value = 10 + (-Math.log(1 - random.nextDouble()) * 2200); // 3. Maioria barata, poucas caras default -> value = 300 + random.nextDouble() * 900; // 4. Compras de mercado e farmácia } if (index % 137 == 0) value += 12000; // Coloca uma compra bem cara de propósito
Como explicar esses 4 tipos de compras de forma simples:
• 1. Variada (Uniforme): Compras comuns entre R$ 20 e R$ 5.000 (qualquer valor tem a mesma chance).
• 2. Na média (Normal/Gaussiana): A maioria das compras fica em torno de R$ 1.800, que é a média do dia a dia.
• 3. Poucas caras (Exponencial): É como a vida real: a imensa maioria das compras é baratinha (um lanche, um café), e só de vez em quando alguém faz uma compra grandona.
• 4. Compras rotineiras (Concentrada): Compras de supermercado ou farmácia entre R$ 300 e R$ 1.200.
• Compras suspeitas: A cada 137 compras, somamos R$ 12.000 para criar compras bem altas de propósito, para o Rafael testar o detector de fraudes dele!
• Cidades: Usamos as cidades da nossa região do Vale do Paraíba: Jacareí, São José dos Campos, Caçapava, Taubaté e Santa Branca.
• Por que usamos SplittableRandom? O gerador de números comum do Java (Random) fica travando quando roda rápido. O SplittableRandom é muito mais moderno e rápido para gerar milhões de dados.

4. Como calculamos a soma e a média: AgregacaoFinanceira.java

Esse é o seu arquivo principal. Ele calcula 4 coisas: Soma total, Média, Maior valor e Menor valor.

A. Modo Sequencial (com 1 thread só)

É um laço for comum de 0 até o final. Uma thread faz tudo sozinha. Ele serve como o nosso tempo de comparação (o tempo base para sabermos se o modo paralelo foi mais rápido mesmo).

B. Modo Paralelo (dividindo o bolo)

Aqui nós dividimos a lista de transações em pedaços iguais para cada thread:

int tamanhoBloco = (transacoes.length + quantidadeTarefas - 1) / quantidadeTarefas;
Por que essa continha aí?
Se você tem 10 compras e 4 threads, uma divisão normal em Java faz 10 / 4 = 2. Quatro threads fariam 4 x 2 = 8 e duas compras ficariam esquecidas fora da conta!
Essa continha (N + T - 1) / T arredonda sempre para cima. Assim, as três primeiras threads pegam 3 compras e a última pega 1. Nenhuma compra fica de fora.

C. Como as threads trabalham sem bater cabeça:

Cada thread roda a sua própria tarefa (Callable<Resultado>):

  • Cada thread cria a sua própria caixinha de resultado (Resultado parcial).
  • Ela soma o pedaço dela em silêncio, sem mexer na memória de nenhuma outra thread.
  • Quando todas terminam, a thread principal pega as caixinhas de cada uma e junta tudo no método mesclar(): soma os totais, pega o maior valor entre eles e recalcula a média final.
  • No final, fechamos o pool com executor.shutdown() para não deixar threads perdidas consumindo memória do computador.

Perguntas

Perguntas do professor e alterações ao vivo

Aqui estão as perguntas que o professor mais costuma fazer, explicadas do jeito mais direto possível.

1. Por que você usou Callable em vez de Runnable nas threads?
Como responder: "Porque o Runnable não devolve nada (o método run() dele é void). Como cada thread estava somando um pedaço das compras, cada uma precisava devolver a sua caixinha de resultado com a soma e o maior valor para a thread principal. O Callable permite retornar um objeto, que a gente pega facilmente com o Future.get()."
2. Por que você não criou uma Thread para cada compra do vetor?
Como responder: "Porque se tivermos 1 milhão de compras e tentarmos criar 1 milhão de threads, o computador trava e dá erro de falta de memória (OutOfMemoryError). As threads do Java gastam memória e tempo do sistema para serem criadas. O jeito certo é criar poucas threads (de acordo com a quantidade de núcleos da máquina, como 2, 4 ou 8) e dividir a lista de compras em blocos entre elas."
3. Por que você não precisou usar synchronized na hora de somar?
Como responder: "Porque cada thread tem a sua própria variável de soma dentro do método dela. Nenhuma thread mexe na variável da outra. Como não tem duas threads tentando escrever no mesmo lugar ao mesmo tempo, não tem perigo de erro e não precisa de travas (synchronized). A junção das somas só é feita no finalzinho, por uma thread só."
